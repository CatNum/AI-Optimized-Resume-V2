## 二、第 1 题：项目总览

### 2.1 面试题

你简历里重点写了“个人职业操作系统 Personal Career OS”，使用了 Coordinator + Worker + Harness 的 Multi-Agent 架构。

请你用 2-3 分钟介绍这个项目，重点回答这几个点：

1. 这个产品解决的核心问题是什么？
2. 为什么要用 Multi-Agent，而不是一个大 prompt / 单 Agent？
3. Coordinator、Worker、Harness 三层分别负责什么？
4. 你在这个项目里最有技术含量的一处设计是什么？

### 2.2 候选人原始回答要点

- 产品最初只是想做一个简单的学习和简历优化工具。
- 后来发现基于简历优化只是单点功能，不能解决长期职业规划问题，也不能评估一次投递或一次简历修改对长期人生选择的影响。
- 因此产品方向逐渐演变为职业规划类工具，并进一步意识到职业规划本质上和个人自身探索、生活方式选择有关。
- 使用 Multi-Agent 的原因是职责需要拆分；如果只用一个大 prompt 或单 Agent，容易出现职责混杂和上下文污染。
- 主 Agent 类似组织架构中的协调者，负责协调、转发、理解 Worker 内容并合成回复。
- Worker 负责具体任务执行。
- Harness 负责对整体流程进行规划和限制，类似为赛马建造赛道，包括 Task 系统、上下文系统、Memory 系统、Skill / Prompt 接入和闸口设置。
- 某些流程未完成时不能进入下一流程，需要 Harness 做判断。
- 最有技术含量的部分是整体架构，包括一主多从、多层分层架构，以及 Agent 层、Harness 层、基础层之间的模块抽取，这对后续扩展比较友好。

### 2.3 面试反馈

这个回答有几个优点：

- 产品动机有演进感：从“简历优化工具”升级到“长期职业决策系统”，能体现你对业务问题的重新抽象。
- 能说出单 Agent 的问题：包括职责混杂、上下文污染、状态容易漂移。
- 能说出 Coordinator、Worker、Harness 的基本分工。

需要改进的地方：

- 口语表达偏散，比如“做着做着”“人生规划类的东西”“什么之类的”较多，面试官会觉得问题边界不清。
- 技术术语必须稳定，例如统一使用 `Multi-Agent`、`Coordinator`、`Worker`、`Harness`、`大 prompt`，避免说成 `moto agent`、`motor`、`honey`、`contract` 等。
- “最有技术含量的是整体架构”这个回答偏虚，需要落到一个具体设计，例如 Harness 的流程约束、HITL 硬拦截、Profile 写入权限、上下文按阶段注入、JSONL trace 或 Agent Eval。

### 2.4 优化版回答

```text
这个产品最初是一个面向 JD 的简历优化工具，但我做的过程中发现，单次简历优化只能解决“这一次怎么投”的问题，不能解决长期职业发展里的目标、能力资产、市场机会、策略推演和简历执行割裂的问题。

所以我把它抽象成一个 Personal Career OS，核心是围绕“身份、能力、市场”三个空间，帮助用户沉淀长期 Profile，分析目标岗位和市场机会，并把这些判断落到阶段性的简历和求职策略上。

我没有用单 Agent 或一个大 prompt，主要是因为这个场景天然有多个职责：用户探索、市场分析、JD 分析、简历策略、简历生成。如果都塞进一个 Agent，容易出现职责混杂、上下文污染、状态漂移和关键操作不可控的问题。

所以我设计了 Coordinator + Worker + Harness 的架构。Coordinator 负责意图识别、任务路由和最终回复合成；Worker 负责具体领域任务，并且 Worker 之间不直接通信；Harness 更像运行时平台，负责阶段流转、上下文注入、工具调用、HITL 闸门、权限校验和 trace 记录。

我认为最有技术含量的是 Harness 层。它不是简单调用模型，而是把 Agent 的执行过程约束在一个可控轨道里，比如五阶段任务流、关键操作确认、Profile 写入白名单、工具超时和错误处理、JSONL trace。这样 Agent 不只是“能回答”，而是变成一个可追踪、可回归、可治理的工程系统。
```

## 三、第 2 题：Harness 拦截机制

### 3.1 面试追问

你刚才说 Harness 是这个项目里最有技术含量的地方。那我追一下：

如果用户在 `explore` 阶段，还没有确认目标岗位，Worker 却试图直接调用“简历生成工具”，你的 Harness 会怎么拦截？

请从这几个角度回答：

1. 拦截规则放在哪里？
2. Coordinator、Worker、Harness 谁负责判断？
3. 拦截后怎么反馈给用户？
4. 这类规则你会用硬编码、配置化，还是 LLM 判断？为什么？

### 3.2 候选人原始回答要点

- 拦截规则主要在 Harness 层完成。
- Harness 会负责判断 Worker 的回复、Coordinator Agent 的最终结果，以及派工过程中的拦截。
- 主要由 Harness 负责判断。
- Harness 中会有硬规则、LLM 软判断和配置化选项。
- Skill、Tool、Prompt、System 上下文等信息会配置化抽取，尽量做到不改代码也能优化效果。
- Harness 拦截后会把信息交给 Coordinator，再由 Coordinator 生成最终回复并反馈给用户。
- 规则分层上，先经过硬规则，再经过软判断，这样可以减少 LLM 调用并节省成本。
- 硬规则主要用于必须完成的流程约束。例如：要进行简历优化，必须先完成简历策略；要进入后续阶段，必须先完成职业初探阶段，否则后续阶段不能推进。

### 3.3 面试反馈

这个回答的方向是对的，尤其是三点：

- 你明确把最终拦截责任放在 Harness，而不是完全交给 Coordinator 或 Worker 自觉遵守。
- 你提到了“硬规则优先 + LLM 软判断回退”，这很符合 Agent 工程里“确定性控制优先”的思路。
- 你提到了配置化，希望 Skill、Tool、Prompt、System 上下文不改代码也能调整，这能体现扩展性意识。

需要加强的地方：

- “Harness 会判断 Worker 回复和 Coordinator 最终结果”这句话还不够精确。更好的表达是：Harness 不只判断自然语言回复，而是在工具调用前、阶段推进前、长期记忆写入前做运行时校验。
- 拦截点要讲清楚：不能只说“在 Harness 里”，要说是在 `tool_call` 执行前、`stage_transition` 前、`profile_write` 前这些关键动作前做校验。
- 规则分层可以更体系化：确定性流程规则用硬规则，业务可变规则配置化，语义模糊场景才用 LLM 判断。
- 用户反馈要更产品化：不是简单告诉用户“不能做”，而是解释缺少哪些前置条件，并引导用户补齐目标岗位、JD 信息或简历策略确认。

### 3.4 优化版回答

```text
这个场景我会把最终拦截责任放在 Harness 层，因为 Worker 和 Coordinator 都可能受到模型输出影响，不能只靠 prompt 约束它们“自觉不调用”。

具体来说，Worker 如果要调用“简历生成工具”，不会直接执行，而是先把 tool_call 请求交给 Harness。Harness 会在工具执行前做一次 pre-check，检查当前 session 的阶段、目标岗位是否确认、JD 分析是否完成、简历策略是否确认，以及这个 Worker 是否有调用该工具的权限。

如果用户还在 explore 阶段，并且目标岗位没有确认，那么这次 tool_call 会被 Harness 拦截。拦截结果会结构化返回给 Coordinator，比如 blocked_action、blocked_reason、missing_requirements、suggested_next_step。Coordinator 再把它转成用户能理解的回复，比如“现在还不能直接生成简历，因为目标岗位和简历策略还没有确认。我们可以先确认你这次要投递的岗位方向，或者进入 JD 分析阶段。”

规则分层上，我会采用硬规则优先、配置化补充、LLM 兜底的方式。像“explore 阶段不能生成简历”“没有确认策略不能进入 resume_optimize”“Worker 只能写自己白名单内的 Profile 路径”这类确定性约束，必须用硬规则或配置规则实现，不能交给 LLM 判断。因为它们关系到流程安全、数据权限和执行边界。

对于一些语义模糊的问题，比如用户的话到底是在闲聊、补充背景，还是已经表达了明确确认意图，可以用轻量 LLM 做辅助判断。但 LLM 判断只能影响软路由，不能绕过 Harness 的硬规则。这样可以兼顾稳定性、成本和灵活性。
```

## 四、第 3 题：Tool / Skill 注册表设计

### 4.1 面试追问

你刚才提到 Skill、Tool、Prompt、System 上下文都尽量配置化，以减少改代码。

那我追问一下：

如果你要设计一个 `Tool Registry`，让不同 Worker 可以注册和调用不同工具，你会怎么设计？

请重点回答：

1. 一个 Tool 的 schema 里应该包含哪些字段？
2. Worker 调用 Tool 前，Harness 应该校验哪些东西？
3. Tool 执行失败、超时、参数错误时，你怎么把错误返回给 Agent？
4. 如果后续要支持 MCP 工具，你这个注册表怎么扩展？
