## 版本范围

v2.2 只承诺以下四项，不自动吸收[产品规划与技术演进](./产品规划与技术演进.md)中的其他 Todo。

### 1. WorkerInvocation

`WorkerInvocation`（Worker 结构化调用契约）把一次 Worker 执行冻结成明确、可校验的调用快照，至少明确：

- `invocation_id`、`node_id` 与 `definition_id`：分别标识本次调用、所属计划节点和采用的注册动作定义。
- `worker_id` 与 `run_kind`：闭合联合的两级判别字段，分别限定 Worker 职责主体和具体业务动作。
- `inputs`：与 `worker_id + run_kind` 对应的具体、深冻结完整输入模型；必需 Outcome 未绑定或输入校验未完成时不能创建调用。
- `goal`：本次调用已经冻结的业务目标。
- `allowed_operations`：本次调用允许执行的业务操作集合。
- `required_skills`：第一次 Worker LLM 调用前必须由 Harness 成功预加载的 Skill。
- `optional_skills`：Worker 可按需加载的授权 Skill 范围。
- `execution_strategy` 与 `deterministic_adapter_id`：选择 ReAct 或确定性 Adapter，并在确定性路径上绑定唯一 Adapter。
- `success_contract_id`：用于选择确定性成功契约的编号。
- `semantic_judge_mode`：声明是否需要语义完成度判断。

`WorkerInvocationRegistry.resolve()`（解析 Worker 调用）是创建完整调用的唯一入口：它根据已验证输入和上游 Outcome 解析具体调用；输入不完整、动作未登记或绑定不合法时不启动 Runner。

本期闭合目录恰好包含 15 个 Run Kind：`identity.exploration_first`、`identity.exploration_revisit`、`capability.exploration_first`、`capability.exploration_revisit`、`capability.jd_bank_deep_dive`、`market.propose_plan`、`market.revise_plan`、`market.start_research`、`opportunity.evaluate`、`strategy.jd_application`、`resume.collect_optimization_levels`、`resume.generate_optimized_resume`、`asset.reuse_outputs`、`asset.register_outputs`、`asset.delete_output`。

### 2. ExecutionPlan

`ExecutionPlan`（执行计划）明确：

- `node`：要执行的业务节点。
- `dependency`：节点之间的依赖关系。
- `order`：在依赖满足后的执行顺序。
- `success condition`：节点成功所需的确定性契约与已验证 Outcome。

依赖未来结果的节点先保存 `ExecutionPlanNodeSpec`（计划节点规格），不能提前伪造输入完整的 `WorkerInvocation`。`ExecutionPlanExecutor.advance()`（推进执行计划）只接受通过身份和状态校验的新结果，并把结果持久化回计划；只有依赖、Gate、授权、必需产物和调用物化全部满足的节点才能进入可执行状态。

### 3. 全局失败机制

全局失败机制统一以下行为：

- 失败分类与标准化 `FailureResult`（失败结果）。
- 按代码策略登记的重试、幂等、核对、降级、补偿和断路器。
- Worker Run、Turn Run 与后台 Job Run 的状态、传播和聚合。
- required operation 硬失败、确定性成功契约和可选语义 Judge 的优先级。
- Trace、Snapshot、Failure Store 和最后诊断出口。
- `TurnResultRenderer`（回合结果渲染器）把内部失败确定性地映射为用户可理解的业务动作与下一步，不暴露堆栈、Provider 或内部 Tool 名称。
- 上游失败时阻断下游；已经确认的上游成果默认保留，除非存在显式登记且安全的补偿。

### 4. 跨模块系统级回归

在全局失败机制完成后，于新的干净临时环境执行跨两份实施计划的最终回归，至少证明：

- 简历生成失败或没有通过成功契约验收时，不产生已验证 HTML delivery。
- `asset.register_outputs` 节点因上游不满足而成为 `blocked_by_upstream`，且不创建虚假的 Asset Worker Run。
- Turn 终态和用户回复反映真实失败，不再由最后一个 Worker 的自然语言摘要掩盖上游失败。
- HTML 已成功但产物登记失败时保留 HTML，并形成可解释的 `partial_success` 对照结果。
- Trace、Failure、Plan、Worker Run 和 Turn Run 身份能够关联并支持回放。

## 已完成

- v2.2 当前没有已完成的业务实现。
- 两份设计规格和两份实施计划已经写成，但“文档已形成”不等于“代码已完成”。

## 进行中

- 在开始实现前保持两份计划的固定依赖顺序：先实施强类型 `WorkerInvocation` / `ExecutionPlan`，再实施全局失败机制。
- 以 Spec 中的闭合类型、唯一 Registry、Success Contract、Outcome Binding 和运行身份不变量作为实现边界。

## 验收标准

- 所有已登记业务动作通过闭合 `WorkerInvocation` 联合进入统一 Runner；真实 Runner、mock、stub 和测试不再消费不同调用模型。
- `ExecutionPlan` 是节点、依赖与累计结果的唯一事实来源；依赖上游 Outcome 的下游调用只能延迟物化。
- `resume.generate_optimized_resume → asset.register_outputs` 必须由已验证 HTML delivery 连接；缺少该 Outcome 时 Asset 不运行。
- 有业务意义的 operation 统一通过 `OperationExecutor.execute()`（执行业务操作）得到确定性结果与策略。
- Worker、Turn 与 Job Run 的失败、部分成功、降级和未知结果有一致状态及传播规则。
- 用户错误呈现与内部 Trace/Failure 证据一致，并避免暴露内部实现细节。
- 干净环境跨模块系统级回归与部分成功对照场景通过。
- 全部非 LLM 回归和静态类型检查通过；LLM Eval 独立记录，不代替确定性契约验收。

## 已知边界

- 四份依赖文档当前工作区已存在，但尚未被 Git 跟踪；由用户后续加入版本库。本 Roadmap 只记录该临时交付边界，不修改、不暂存这些文件。
- 强类型调用实施计划是全局失败机制实施计划的必需前置；不能并行落地后再靠适配层长期维持两套事实源。
- 计划不修复旧 demo 运行记录，最终 Bug 回归只在新的干净临时环境执行。
- `market.start_research` 的 Worker Run 只验收后台 Job 已被接受并持久化；后台 Job 的后续终态独立管理。
- 该版本不承诺跨进程或应用重启恢复全部旧执行；授权暂停点的恢复范围以强类型调用 Spec/Plan 为准。

## 非目标

以下均为长期候选或尚未承诺事项，不属于 v2.2：

- 长期记忆索引、side-query、去重、合并和剪枝。
- session memory 的上下文压缩策略。
- 简历模板 Skill、模板解析 Agent 和用户自定义模板。
- Offer 对比与选择。
- 评测 Agent 或新的通用 benchmark 产品。
- 市场 Agent 自动后台前移。
- 城市、专业、定居、婚姻时间点等扩展人生规划能力。
- 纯规划链及 `strategy.career_plan`；它们需先确认如何融合现有 pipeline，再单独扩展闭合类型、Prompt、契约和验收。
- 新的 Multi-Agent 组织形态、审批 Agent 或 Agent 通知机制。
- 简历脱敏、三档 HTML 顺序复用和未确认的业务流程优化。
