## 产品愿景与代际演进

- **V1**：主要功能是根据 JD 修改简历，判断是否符合职业规划是次要功能。
- **V2（当前代际）**：以长期规划为主，根据 JD 修改简历是其中一个功能。产品不再只聚焦单次 JD 投递，而是成为由长期职业记忆、职业资本推演与简历 HTML 交付构成的个人职业操作系统。
- **V3**：在能力扩展到多行业、多岗位时进入“寻找自己”的阶段。
  - 规划的本质是找自己、向内求。每个人的自己不同，别人的成功不一定适合自己。
  - “人生规划系统”也可以理解成“寻找自己的系统”：人生规划不是要求成为多成功的人，而是在寻找自己的路上不断接近、最终成为自己；无论经历怎样的路程，也无论是否取得世俗意义上的成功，最终都应回到最初的自己。
  - 自己的偏好比外界定义的成功更重要，规划路径不应主要由外部成功样本引导。

## Harness 与模型边界思考

1. 如何做出能随着模型能力提升而提升的 Harness 产品？
   - 需要持续明确哪些约束由 Harness 管、哪些判断由模型管。
   - 需要判断 Harness 是否应该与具体业务绑定，详见本文“设计示例”。
   - 类比教孩子：不会分别把“分析销售数据”和“分析用户行为数据”作为两套大脑逻辑教授；如果每个业务都必须单独教 LLM，可能说明能力仍应由大脑演进，而不是固化进 Harness。
2. Agent 如何切割，边界是否可以像微服务一样定义？
3. 大脑才负责决策。
   - 组织按部门分层，是为了逐层精炼信息并汇总到最高决策层。
   - Agent 架构是否也应该以逐层精炼、最终集中决策的方式组织，仍需验证。
4. Go + Python 如何切割已不再是当前问题：原记录已决策“v0.1 纯 Python”，当前 V2 架构继续采用 Python 单体，见[应用运行时与部署](../architecture/04-应用运行时与部署.md)。

### Agent 架构与编排

- 针对不同岗位由不同 Agent 支持的 Multi-Agent 架构：
  - 路由从关键词适配，演进到语义向量适配，再到大模型路由。
  - 比较或组合 ReAct 与 Plan And Execute 架构。
  - 候选方案包括审批 Agent，对其他 Agent 结果进行审批。
- 继续验证 LangGraph 编排服务及“专业领域 Agent + HR Agent”的组合是否必要。
- 深挖业务流程：
  - 获取 JD、候选人信息（简历和尽可能细的过往经历）、候选人偏好等基本信息。
  - 以面试官视角或循序追问的方式深挖简历背后的完整经历；简历只是经历的浓缩，不等于全部经历。
  - 判断 JD 与候选人信息是否强不一致。
  - 判断候选人是否准备转行。
- 继续回答“是否真的需要 Multi-Agent”：
  - 对同步流程，可能只需为不同流程维护不同 system prompt、Tool、Skill 等配套；一次 API 调用已经可以视为一个 Agent。
  - 若没有异步提速或 Token 爆炸问题，未必需要子 Agent。
  - 多流程 Agent 可以理解为父子型；多份简历或简历模块并发可以理解为主从型，但简历优化吞吐量较小，是否值得使用主从型仍待确认。
  - 主从型的明确优势是异步并行。
- Agent 间通知机制需要优化。

### 记忆、上下文与动态任务

- 长期记忆系统：
  - 确认长期记忆应存储哪些信息，以及每类 Agent 执行时应读取哪些信息，参考[职业档案 PRD](../prd/A01.%20机制-职业档案%20PRD.md)。
  - 文件增多后支持去重、合并和剪枝。
  - 增加常驻 System Prompt 的索引，正文按需加载。
  - 候选检索方式是把索引文件通过 side-query 发给 LLM 选择；side-query 遇到 API 错误或 JSON 解析失败时，降级为 `name + description` 关键词匹配。
- 上下文压缩：
  - `session memory` 负责同一会话的连续性，并明确 compact 后仍需保留的上下文。
  - Memory 管长期知识，session memory 管当前会话压缩后的续接，两者配合使用。
- Task 系统与动态任务：
  - 当前大任务流程仍偏固定，需要根据用户消息动态生成大任务内部的小步骤。
  - 需要定义什么条件下任务应拆成多任务列表。
- 简历优化数据范围仍需用质量和成本证据决策：候选观点是全量数据传递更准确，分阶段裁剪主要用于节省 Token，但节省是否值得仍未确认。

## 已形成设计、待实施

### 强类型 Worker 调用与执行计划

当前 Coordinator 主要传递 `worker_id`（Worker 标识）与自然语言 `goal`（执行目标）。当同一个 Worker 承担多个业务动作时，它可能根据用户原话和零散 Session 状态猜测职责，从而选错 Skill mode、调用错误 Tool、遗漏必需输入，或在上游未成功时错误串行下游 Worker。

已经形成以下设计，但没有实现完成：

- `WorkerInvocation`（Worker 结构化调用契约）至少明确：
  - `invocation_id`、`node_id` 与 `definition_id`：分别标识本次调用、所属计划节点和采用的动作定义，用于把执行、计划与注册表定义关联起来。
  - `worker_id` 与 `run_kind`：闭合联合的两级判别字段，分别限定职责主体和具体业务动作。
  - `inputs`：与 `worker_id + run_kind` 对应的具体、深冻结完整输入模型；它只能在必需 Outcome 绑定和输入校验完成后生成。
  - `goal`：本次调用的业务目标，用于给 Runner 提供已冻结的目标上下文。
  - `allowed_operations`：本次调用允许执行的业务操作。
  - `required_skills`：首次 Worker LLM 调用前必须加载的 Skill。
  - `optional_skills`：Worker 可按需加载的授权 Skill 范围。
  - `execution_strategy` 与 `deterministic_adapter_id`：选择 ReAct 或确定性 Adapter，并在确定性路径上绑定唯一 Adapter。
  - `success_contract_id`：选择哪条确定性成功契约验收输出。
  - `semantic_judge_mode`：声明是否需要语义完成度判断。
- `ExecutionPlan`（执行计划）保存节点、依赖、顺序、成功条件和已验证结果；依赖上游结果的节点不能提前伪造完整调用。

## 设计示例

### 示例 1：Harness 应该与业务有关吗？

下面这份 Skill 的描述来自 hello-agents，但是这个描述与业务强相关。

是否应该抽取 `Text → SQL` 这一层抽象，再让 LLM 这个“大脑”填充实际业务？

这样 Harness 工程可以与具体业务分离，随 LLM 能力提升而提升，也能适配多种业务场景。

```yaml
description: >
  将中文业务问题转换为 SQL 查询并分析 MySQL employees 示例数据库。
  适用于员工信息查询、薪资统计、部门分析、职位变动历史等场景。
  当用户询问关于员工、薪资、部门的数据时使用此技能。
```
