## 版本号规则

版本按 `v2.1 → v2.2 → ... → v3.1` 演进：

- `v2.x`：产品代际目标仍属于 V2，即以长期职业规划为主，JD 分析与简历 HTML 交付是其中一条闭环；同一代际内按 `v2.1`、`v2.2` 顺序递增。
- `v3.1`：产品代际目标发生变化，进入 V3“寻找自己”的多行业、多岗位探索；新代际从 `.1` 开始。
- 路线版本只表达产品承诺，不与包版本、数据库版本或单份实施计划编号绑定。
- 未确认版本归属的想法只进入[产品规划与技术演进](./产品规划与技术演进.md)的候选池，不自动占用下一个版本。

## 状态定义

| 状态 | 含义 |
|---|---|
| 规划中 | 版本目标与范围已被明确记录，但尚未以实现和验收证据证明完成 |
| 开发中 | 已进入实现或验证阶段，允许同时存在已完成项、进行中项和已知边界 |
| 已完成 | 版本范围已经实现，并有与验收标准对应的代码、自动化测试、运行截图或可复现记录 |
| 已归档 | 版本或候选事项不再继续推进；必须说明归档原因、替代方案或后继版本，不能把归档等同于完成 |

## Roadmap 与 Superpowers Spec/Plan 的边界

- Roadmap 负责“为什么做、在哪个产品版本做、版本承诺到什么程度、用什么证据变更状态”。
- Superpowers Spec 负责“系统应满足什么设计约束、领域模型和行为不变量”。
- Superpowers Plan 负责“按什么任务、文件和验证步骤实施”。
- Roadmap 可以链接 Spec/Plan，但不复制其全部实现步骤；Spec/Plan 完成也只代表设计或计划交付完成，不自动证明业务代码已经实现。
- 具体需求仍以 `docs/prd/` 为产品需求事实源，架构现状仍以 `docs/architecture/` 和当前代码为准。

## 状态变更与证据要求

1. `规划中 → 开发中`：需要确认版本目标、范围、非目标、验收标准和责任边界；仅有灵感或 Todo 不足以进入开发中。
2. `开发中 → 已完成`：每项“已完成”必须链接到当前代码、自动化测试、运行截图或可复现验证记录；只有 Spec、Plan、Prompt 或未执行的测试清单不能作为完成证据。
3. `规划中/开发中 → 已归档`：必须记录日期、原因以及替代方向；未实现事项不得通过归档表述成已交付。
4. 证据变化时同步修订版本文档；测试数量和通过情况只记录实际执行快照，不沿用可能过期的历史数字。
5. 版本范围新增承诺前先更新 Roadmap；长期候选能力不会因为与下一版本相关就被默认吸收。
