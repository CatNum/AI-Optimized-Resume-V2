## 0. 摘要

当前 `browser_fetch` 只是返回固定 `example.com` 的占位工具，无法证明市场 Worker 使用了真实、近期、可审计的市场信息。本 spec 删除通用 `browser_fetch` 方案，新增面向市场阶段的深模块 `market_research`：用户先确认不可变调研方案，系统再通过专用可见 Google Chrome 和 DrissionPage 获取 BOSS 直聘当前岗位与 Google Trends 搜索关注度，完成受限 LLM 语义提取、程序确定性统计和市场 Worker 归纳，最后以普通 assistant 回复在聊天中交付结果。

本功能的目标不是建设生产级爬虫平台，而是形成一条可在简历和面试中深入讲解、现场演示并经得住追问的 AI 链路：

1. **真实网页闭环**：BOSS 提供当前岗位、职责、要求、学历、经验、技能和薪资；Google Trends 只提供搜索关注度变化。
2. **LLM 与确定性程序分工**：LLM 发现技能、提取语义并归纳结果；程序负责字段解析、去重、计数、比例、分组和薪资中位数。
3. **Harness 硬约束**：市场 Worker 只有提案权和启动权；用户确认、方案冻结、工具权限、流程阻塞和结果校验由 Harness 执行。
4. **人机协同浏览器**：系统不自动破解验证码；遇到登录或验证时暂停，等待用户在专用 Chrome 中处理。
5. **可审计结果**：保存清洗后的结构化岗位、LLM 提取并通过依据校验的职责/要求/技能、技能词表、Trace、少量完整网页截图和结果版本；原始 JD 与完整 HTML 不写入磁盘。页面级人工审计只依靠成功岗位中 10% 的完整网页截图进行抽样，不承诺对每条语义结论保留逐字原文证据。
6. **明确推断边界**：BOSS 不回答岗位需求强弱或招聘趋势；Google Trends 是低置信度的搜索关注度侧面信号，不等于招聘趋势。

## Problem Statement

用户在职业初探后，需要了解目标职业方向当前实际需要什么，才能在后续步骤中判断职业相关性、机会价值、能力差距和简历策略。当前占位工具存在以下问题：

- 没有真实搜索或网页采集，市场结论可能来自模型训练知识。
- 调研范围没有受第一步用户信息和用户确认约束，容易泛泛分析整个岗位市场。
- 通用搜索无法稳定获得 BOSS 当前岗位的薪资、经验、学历、职责和技能字段。
- LLM 若同时负责抽取、计数和结论，难以证明数字未被编造或算错。
- 当前同步 ReAct 工具调用不能自然表达可见浏览器、人工登录、进度、暂停、继续和取消。
- 市场结果没有独立的 demo 级长期存储，无法跨 Session 提示复用或进行人工审计。
- 市场阶段与下游机会判断的职责不清，容易提前把市场事实和用户匹配混在一起。

本问题不是“把搜索 API 换成浏览器”这么简单，而是要建立一条受 Harness 约束的真实数据获取与 AI 分析链路，同时主动限制工程范围，使其服务于项目深挖、简历表达和面试证明。

## Solution

系统在职业初探完成后，由市场 Worker 根据 `exploration.*` 与 `capability.*` 生成 1～3 个候选职业方向的方案提案。Coordinator 只负责接收、校验输出类型和编排后续交互；真正的 `ResearchPlan` 由 Harness 管理的 `MarketResearchPlanStore` 创建、版本化和冻结，市场 Worker 与 Coordinator 都不能自行持久化或改写方案。用户确认职业方向、关键词、城市和工作年限口径后，Harness 允许市场 Worker 调用 `market_research(plan_id)`。

一次调研包含一个主任务和最多三个顺序执行的职业方向子任务。每个方向先获取 Google Trends，再在同一个专用 Chrome 标签页中按关键词和城市顺序采集 BOSS 岗位。单方向的 Google Trends、BOSS 页面操作和岗位提取 LLM 共用 10 分钟预算；人工登录或验证等待、最终确定性统计和市场 Worker 报告生成不计入该预算。

采集线程只把原始 JD 保留在内存中。每个搜索词的前 10 条岗位触发第一轮受限 LLM 提取，中间 10 条先排除已有技能再触发第二轮，后 10 条不再发现新技能。持久化岗位中的职责、要求、优先条件、岗位证据和语义技能均来自通过依据校验的 LLM 提取结果，不保存对应 JD 原文；页面级人工审计仅使用 10% 完整网页截图抽样。随后程序生成冻结统计，受限市场 Worker 生成职业定义、职责主题、要求归纳、岗位证据主题和方向对照。Harness 合并确定性字段并验证所有岗位引用，纯文本渲染器生成最终聊天回复。

调研运行期间聊天 Pipeline 被硬阻塞；聊天窗口只展示进度、继续和取消。至少一个职业方向成功即可发布部分成功结果。用户查看结果后明确确认，Pipeline 才能进入下游步骤。

## User Stories

1. 作为求职用户，我希望市场调研基于职业初探得到的个人方向，而不是泛泛搜索所有岗位。
2. 作为求职用户，我希望先确认职业方向和调研条件，再启动浏览器，以免系统调研错误范围。
3. 作为求职用户，我希望看到系统实际使用的关键词、城市、经验口径和筛选条件。
4. 作为求职用户，我希望系统打开一个独立可见 Chrome，以便我知道网页正在真实运行。
5. 作为求职用户，我希望登录和验证码由我手动处理，以免系统保存密码或绕过平台验证。
6. 作为求职用户，我希望调研期间看到当前方向、关键词、城市、候选岗位数和阶段。
7. 作为求职用户，我希望调研期间不能提前执行依赖市场结果的后续任务。
8. 作为求职用户，我希望可以取消调研，并确保未发布的岗位与截图被删除。
9. 作为求职用户，我希望 BOSS 结果只包含全职、有效薪资且招聘者近期活跃的岗位。
10. 作为求职用户，我希望薪资必须同时包含上下限，面议或单边薪资不能污染统计。
11. 作为求职用户，我希望系统重点分析与我工作年限相关的岗位，同时简述入门到高级的变化。
12. 作为转行用户，我希望工作年限口径使用目标职业相关经验；不明确时系统先询问我。
13. 作为求职用户，我希望职责、要求和技能结论能够追溯到真实岗位编号和链接。
14. 作为求职用户，我希望薪资、经验、学历、行业和公司规模由程序统计，而不是由 LLM 猜测。
15. 作为求职用户，我希望 Google Trends 被明确称为搜索关注度，不被包装成招聘趋势。
16. 作为求职用户，我希望搜索词走势分化或长短期走势相反时，系统如实说明。
17. 作为求职用户，我希望样本不足时仍能看到有限结果，但明确知道参考价值有限。
18. 作为求职用户，我希望不同职业方向独立调研；一个方向失败不拖累已经成功的方向。
19. 作为求职用户，我希望多方向结果只做并列对照，不自动排名、评分或推荐。
20. 作为求职用户，我希望六个月内发现同方向历史结果时，由我决定复用还是重新获取。
21. 作为求职用户，我希望复用时看到原始调研时间、城市、关键词、样本数和过期时间。
22. 作为求职用户，我希望手动重新调研时获取最新网页数据，而不是静默复用旧数据。
23. 作为求职用户，我希望可以删除历史市场调研数据及其审计截图。
24. 作为市场 Worker，我希望只提交调研提案和已确认 `plan_id`，不处理浏览器细节。
25. 作为市场 Worker，我希望最终综合时只读取冻结数据，不能修改程序统计。
26. 作为 Coordinator，我希望调研未完成时有硬闸门阻止后续 Worker 调度。
27. 作为 Opportunity Worker，我希望只读取正式市场结果，不自行重新抓取网页。
28. 作为开发者，我希望 BOSS、Trends、语义提取、确定性统计和综合归纳职责清晰。
29. 作为开发者，我希望网页中的提示词注入不能获得工具、Profile 或本地文件权限。
30. 作为开发者，我希望结果、截图、浏览器 Profile 和不同 demo 严格隔离。
31. 作为项目讲解者，我希望能够用真实问题、设计决策、代码、异常场景、结果和取舍完整讲解该功能。

## Implementation Decisions

### 1. 产品与阶段边界

- 市场阶段只回答外部市场基线，不做用户能力匹配、转行相关性判断、职业评分或推荐。
- BOSS 只回答当前岗位职责、任职要求、经验、学历、技能、薪资、公司行业和公司规模。
- Google Trends 只回答中国地区过去 1 年与最近 3 个月的搜索关注度变化。
- 不输出“岗位需求强弱”或“招聘趋势”。Google Trends 只能作为低置信度的市场热度侧面信号，并必须声明不代表招聘趋势。
- 下游步骤可以基于正式市场结果进行职业相关性、能力差距和决策，但不能直接读取全量岗位、截图或临时数据。

### 2. 职业方向与调研方案

- 市场 Worker 根据 `exploration.*` 与 `capability.*` 提出 1～3 个职业方向，只生成结构化提案，不创建持久化方案。
- Coordinator 只接收并编排提案，不自行拼装、补写或冻结业务字段；Harness 的 `MarketResearchPlanStore` 是 `ResearchPlan` 的唯一创建者和写入者，负责默认值、数量校验、版本、哈希、确认和消费。
- 每个方向最多 3 个 BOSS 搜索词和 3 个 Google Trends 近义搜索词；两组词独立管理。
- 未指定城市时使用北京、上海、深圳、杭州；用户指定时按用户给出的最多 4 个城市及顺序执行，不限于默认四城。
- 首期不支持“全国”采集，不做城市间岗位数量、薪资或技能对比。
- 同方向开发使用总工作年限；转行使用目标职业相关经验；无法判断时必须先询问用户。
- 调研方案包含 `plan_id`、版本、状态、方向、关键词、城市、经验口径、不可变 `filter_policy`、600 秒预算、生成与确认时间、`plan_hash` 和来源 Session。`filter_policy` 明确保存全职、允许的招聘者活跃度、双边有效薪资、公司岗位上限和不使用发布日期过滤等固定筛选条件。
- 市场 Worker 在方案阶段只有提案权；方案确认后的启动阶段只能提交已确认 `plan_id` 调用 `market_research`，不能改写方案内容。Harness 校验数量上限并持久化方案；用户修改会生成新版本并使旧确认失效。
- 启动前必须在聊天中展示完整条件预览。用户可以修改职业方向、关键词、城市及顺序和经验口径；系统只在最终一次明确“开始调研”确认后启动浏览器。
- 用户确认后方案冻结。`market_research` 只接收 `plan_id`，不得接收 LLM 临时生成的关键词或城市。
- 已启动方案标记为 `consumed`，手动重新调研必须生成并再次确认新方案。

新市场调研链路的任何产物都禁止写入 `prior_results.market`，包括方案提案、异步启动回执、未确认结果和正式结果。`prior_results.market`（历史市场 Worker 结果）是旧同步链路遗留字段，新链路不再把它作为完成标志、派工授权、路由依据、JD 上下文证据或下游数据源。

### 3. 外部 seam、工具权限与响应

- 删除 `browser_fetch`，外部工具固定为 `market_research`。
- 市场 Worker 只能用它启动已确认方案；Opportunity Worker 不再拥有浏览器工具。
- 继续和取消由生命周期 API 调用共享 `MarketResearchService` 执行；Coordinator 不控制浏览器生命周期，只在 Harness 闸门通过后执行流程解锁与后续 Worker 编排。
- 最终综合模式的市场 Worker 不拥有任何工具。
- `market_research(plan_id)` 返回 `accepted`、`research_id`、`plan_id`、初始 `status`、简短 `message` 和可选 `error_code`，不等待最终报告。
- Worker ReAct Runner 收到 `accepted=true` 后必须立即返回专用的 `accepted_async` 运行结果；Coordinator 只处理该运行结果并停止本轮委派，不能把异步启动误判为市场 Worker 已完成。
- 市场调研管理模块内部提供启动、读取状态、继续、取消和发布结果的生命周期操作；这些操作不作为 LLM 可自由填写的 `action` 参数。
- `plan_id` 存在、已确认、哈希一致且未被消费，是启动任务的 Harness 硬前置条件。
- `artifacts.market` 的方案、运行和结果引用是市场阶段生命周期 SSOT；Coordinator 的通用 Worker 完成逻辑必须对市场提案和 `accepted_async` 特殊处理，不能用完整 Worker 输出覆盖该结构。
- Opportunity Worker 的前置检查不得再判断 `"market" in prior_results`。Harness 必须通过 `result_ref` 或 `reuse_ref` 调用 `resolve_downstream_result()`，重新校验结果存在、版本有效、未删除、未过期且已经用户确认，再把精简正式结果注入专用下游上下文。
- `profile_memory` 不得把 `artifacts.market` 的生命周期信封当成市场业务数据，也不得回退读取旧 `prior_results.market`。通用 `attach_profile_memory_to_context()`（向 Worker 上下文附加档案记忆）不再注入市场结果；Harness 在 Opportunity 派工校验通过后，才把 `resolve_downstream_result()` 返回值放入专用 `context.market_research_result`。

### 4. 主任务、方向子任务与单任务锁

- 一次用户确认创建一个 `research_id`，其下最多三个 `direction_run_id`。
- 多方向按照预览顺序、使用同一个专用 Chrome 串行执行，禁止并发浏览器或并行标签页。
- 每个 demo 同时只允许一个活动运行；活动运行可以是主任务或 `DirectionRetryRun`。其他 Session 只能看到已有运行摘要，不能接管或取消。启动时必须在同一进程级临界区内完成“检查活动运行、写入 `queued` 占位、消费方案”，禁止仅通过先读后写 `index.json` 实现表面锁。
- 每个方向内部的 BOSS 与 Google Trends 是原子数据组合，不允许复用旧 BOSS 搭配新 Trends。
- 至少一个方向成功即可生成最终结果；对照只包含成功方向。
- 失败方向临时数据删除，只保留最小错误事件，并允许只重试该方向。

### 5. 异步执行与聊天阻塞

- 首期使用 FastAPI 进程内的专用后台线程运行 `MarketResearchRunner`，不引入 Celery、Redis、独立任务子进程或文件 IPC。
- DrissionPage 的创建、页面操作和关闭始终在该线程内完成。
- 继续和取消使用线程事件；`status.json` 用于页面刷新后的状态恢复。工具 Handler、生命周期 API 和 FastAPI lifespan 必须共享同一个应用级 `MarketResearchService` 与 Runner 注册表，不能各自创建互不相通的 Service 实例。
- 应用重启不续跑未完成任务，而是标记 `process_interrupted`、删除临时数据并要求重新调研。
- 后台异步只解决 HTTP/LLM 调用阻塞；业务 Pipeline 仍严格串行。调研终态之前禁止调度下游 Worker。
- 状态卡每 2 秒读取一次状态，原位展示阶段、方向、关键词、城市、候选数、有效数和耗时；普通进度不写入聊天历史。
- `running` 时输入区锁定并只保留取消；`waiting_user` 时只允许继续或取消。
- 报告完成后作为普通 assistant 回复写入聊天，不增加特殊消息类型；`completion_published_at` 防止重复投递。
- 发布后仍停留在市场阶段，用户明确确认“继续下一步”后才推进 Pipeline。
- 前端点击“开始调研”时，聊天请求必须携带结构化 `market_action=start_confirmed_plan`；后端校验当前 Session 的 `active_plan_id` 已确认后，确定性路由到市场 Worker。显示文本“开始调研”只用于聊天记录和用户理解，不作为唯一意图判定依据。
- 正式结果发布后，Harness 写入 `market_result_confirmation` pending gate。按钮调用确认 API；自然语言“继续下一步”等输入复用现有 gate 匹配器，只有明确确认才设置 `market_result_confirmed=true`，并把当前不可变 `result_ref|reuse_ref` 复制为 `confirmed_result_ref` 后推进阶段。Resolver 必须要求当前引用与 `confirmed_result_ref` 完全一致；拒绝或含义不明时继续停留在市场阶段。

### 6. 状态机

主任务状态包括：

- `queued`：等待后台线程执行。
- `running`：正在执行。
- `waiting_user`：等待用户登录或处理验证。
- `cancelling`：正在停止任务并清理。
- `completed`：所有方向成功。
- `partial_completed`：至少一个方向成功、至少一个方向失败。
- `failed`：没有任何方向成功。
- `cancelled`：用户取消且清理完成。

执行阶段包括启动浏览器、获取 Trends、采集 BOSS、语义提取、确定性统计、市场综合、持久化和结束。主任务终态不可回退。

失败方向重试使用独立 `DirectionRetryRun`（方向重试运行），创建新的 `direction_run_id` 并拥有自己的 `queued/running/waiting_user/cancelling/completed/failed/cancelled` 状态。原 `research_id` 的 `completed|partial_completed|failed` 终态保持不变；状态 API 同时返回主任务终态和当前重试状态。重试运行占用同一个 demo 活动任务锁，复用继续、取消、人工登录等待和中断清理规则；成功时只发布新的 `result_version`，失败或取消不修改上一正式版本。

允许的取消转移包括 `queued|running|waiting_user -> cancelling -> cancelled`，确保任务仍在排队时前端展示的取消操作真实可用。

需要用户操作时，Harness 写入只允许继续或取消的 `pending_gate`。自然语言含义不明确时保持等待，不允许 Coordinator 借机调度其他任务。

### 7. 专用 Chrome 与 DrissionPage

- 首期仅在用户本机运行，使用已安装的 Google Chrome；不自动下载 Chromium。
- 默认按操作系统常见位置寻找 Chrome，支持集中配置覆盖可执行文件路径。
- 使用当前 demo 独立的 `market_research/browser_profile/`，不附加用户日常 Chrome Profile。
- 始终可见、单浏览器、单标签页、顺序低频操作；调研完成或取消后自动关闭。
- 只有等待用户登录或验证时保持浏览器打开，且不设置自动等待超时。
- 系统不保存密码、短信验证码，不破解验证码，不使用代理、账号池或多个浏览器。
- 应用记录专用 Chrome PID，只终止由当前 demo 启动的专用进程，绝不按名称批量关闭用户 Chrome。
- 未找到或无法启动 Chrome 时返回 `browser_failed`，不回退到 Safari、无头浏览器或日常 Profile。

### 8. 页面契约与安全导航

- BOSS 和 Google Trends 分别维护版本化页面字段契约，集中描述 URL、登录标识、筛选器、列表、详情和对比卡关键字段。
- 关键字段失效时返回 `page_changed`，不让 LLM读取整页猜测，也不盲目点击。
- BOSS 只允许访问 HTTPS 的官方域名；Trends 只允许访问 HTTPS 的官方域名。
- 岗位链接打开前重新校验域名；拒绝本地地址、`file:`、`javascript:`、短链和第三方跳转。
- JD 中出现的链接一律不点击。
- 页面失败只保存页面契约版本、阶段、字段名和错误码；不保存失败截图、DOM 或异常页面证据。

### 9. Google Trends 采集

- 每个方向先获取 Google Trends，再用剩余时间采集 BOSS，避免 10 分钟被 BOSS 全部消耗后方向因缺少 Trends 而失败。
- 地区固定为中国；时间窗口为过去 1 年和最近 3 个月。
- 每个方向最多三个近义词。对每个词分别选择“过去 1 年”和“最近 3 个月”，读取“热度随时间变化的趋势”区域中页面直接显示的比较卡片，包括上升/下降方向、百分比和“与过去 1 年相比”或对应窗口的比较标签。
- 比较卡片表达的是当前所选窗口与其前一个等长窗口的页面比较；它不同于折线图的 0～100 归一化时间序列，也不同于“相关搜索”中的上升关键词百分比。结果必须保存 `metric_kind=visible_period_comparison` 和页面原始比较标签，禁止混用三种口径。
- 不下载 CSV，不读取或自行聚合折线图点位，不计算自定义均值、阈值、斜率或综合涨幅。
- 全部有效关键词方向一致时才概括整体方向；不一致时报告“搜索词走势分化”。
- 一年与三个月方向相反时分别描述长期和近期变化，不合成为单一结论。
- 页面正常但无比较卡片或无数据时分别记录 `trend_comparison_unavailable` 或 `trend_no_data`，不根据折线图自行推断百分比，方向仍可完成；页面技术失败时该方向失败。
- 每条记录保存查询词、地区、时间范围、`metric_kind`、趋势方向、页面百分比、比较标签、页面 URL、采集时间和契约版本，不保存 Trends 截图。

### 10. BOSS 搜索、城市顺序与时间预算

- BOSS 搜索前直接设置求职类型为全职。
- 每个搜索词目标为 30 条全局去重后的新增采集有效岗位，最多三个搜索词、即最多 90 条唯一岗位。
- 重复岗位只更新 `matched_keywords`，不占后续搜索词额度。
- 默认城市严格按北京、上海、深圳、杭州补足；用户指定时按用户顺序执行。累计达到 30 条后不再搜索后续城市。
- 最终结果展示实际覆盖城市，不暗示四城都被搜索，也不把岗位数解释为市场总量、需求强弱或城市排名。
- 搜索词严格顺序执行，不做时间切片。后续搜索词可能因 10 分钟到期未执行，结果必须显示“完成、截止或未执行”状态。
- 使用 BOSS 页面默认排序，不尝试控制或推断平台排序算法。结果必须说明样本可能受到 BOSS 默认排序、账号状态和个性化推荐影响。
- Google Trends、BOSS 页面和岗位提取 LLM 共用每方向 600 秒预算；人工登录或验证等待暂停计时。
- 最终确定性统计与市场 Worker 综合不计入 600 秒。
- 到点后不再启动新的常规网页或 LLM 操作，已经发出的操作允许完成。
- 若到点时尚未发起任何一次岗位提取 LLM，但已有至少一条采集有效岗位，则允许在预算外执行一次兜底提取；失败子集仍可重试一次。这是唯一预算例外。
- 页面点击或返回间等待 1.5～3 秒，切换城市或关键词等待 2～5 秒；连续三次滚动没有新岗位时进入下一城市。所有自动等待计入预算。

### 11. 采集有效岗位与页面字段

`collection_valid` 表示岗位可参与确定性统计，必须同时满足：

- 详情页可访问、岗位未关闭。
- 有稳定 `job_id` 或可计算指纹、岗位链接、标题和城市。
- 有基本可用岗位描述，且至少存在职责或要求信息。
- 已筛选全职。
- 招聘者活跃度为“刚刚活跃”“今日活跃”或“3 日内活跃”；页面原始值按去除空白后的 `3日内活跃` 解析。
- 可同时解析 `salary_min` 和 `salary_max`。

不设置岗位发布日期筛选，也不根据发布日期形成结论。“当前岗位样本”只表示本轮抓取时仍可访问、满足全职、薪资和招聘者活跃度规则的岗位。

不采集城市内区或地点，不采集福利标签、招聘者姓名、联系方式、融资阶段、公司介绍、评论或员工评价。公司只保存名称、唯一标识、行业和规模，用于去重与分布统计，不做公司评价。

岗位结构化字段包括岗位编号与 URL、标题、命中搜索词、城市、经验原值与分组、学历原值与分组、薪资上下限、招聘者活跃度、公司标识、公司名称、行业、规模、采集时间，以及通过依据校验的 LLM 职责、要求、优先条件、岗位证据和语义技能提取结果。结构化岗位禁止保存原始 JD、JD 片段或为了长期审计而保留的逐字原文依据；没有通过语义校验的岗位只保存确定性元数据。

列表卡片与详情页冲突时以详情页为准；关键字段无法从详情页可靠解析时岗位无效，不用列表卡片猜测补齐。

### 12. 薪资、经验与学历解析

- `salary_min` 与 `salary_max` 只保存税前人民币元/月整数。
- 接受明确的双边月薪区间；`K` 乘以 1000。
- 年薪双边区间除以 12；下限向下取整、上限向上取整。
- `·13薪` 等月数、奖金、股票、补贴和总包不纳入上下限。
- 面议、单边上下界、单个数字、缺少单位，以及元/时、元/天、元/周等单位无效。
- 校验薪资下限大于 0，且上限不小于下限。
- 经验与学历同时保存页面原值和程序标准化分组，以便审计映射是否正确；未知新标签保留原值并归入未识别，不让 LLM猜测。
- 经验统一映射为不限/应届或一年以内、1～3、3～5、5～10、10 年以上和未注明。
- 学历统一映射为不限、初中及以下、高中/中专、大专、本科、硕士、博士和未注明。

### 13. 去重、公司上限与截图

- 先用 `job_id` 全局去重；没有 ID 时使用公司名称、岗位标题、城市、薪资上下限和清洗后描述哈希生成岗位指纹。
- 同公司同标题但不同城市视为不同岗位。
- 公司判定优先使用 `company_id`，无法取得时使用规范化公司名称。
- 同一职业方向按抓取顺序只保留同公司前 5 条采集有效岗位；第 6 条起跳过，不获取该公司全部岗位后再择优。
- 只有通过有效性、去重和公司上限并确定进入样本的岗位，才独立执行 10% 截图概率判断。
- 命中后保存完整网页长截图，不遮蔽招聘者姓名、头像或其他页面内容。
- 截图是本功能唯一长期保留的页面级原始审计证据，只用于本地人工抽样审计，不提供给 LLM、不参与统计、不进入下游。10% 抽样用于检查页面与结构化结果是否大体一致，不构成每条职责、要求或技能结论的完整逐项证据。
- 成功调研截图随审计数据长期保留，直到用户手动删除；取消、方向失败或未发布结果的截图必须删除。

### 14. 原始 JD、受限 LLM 提取与三段策略

- 原始 JD 由 DrissionPage 从岗位详情页读取，只存在于调研线程内存中；不写入磁盘、不进入长期结果，也不保存完整 HTML。职责、要求、优先条件、岗位证据和语义技能只保存 LLM 提取后的结构化结果；用于校验提取结果的最短原文依据在内存校验完成后立即丢弃。
- 岗位提取复用现有 Worker 模型，温度为 0；不新增专用模型角色。
- 提取模型不读取 Profile、聊天历史、Cookie、截图或文件路径，没有任何工具权限。
- 输入以带 `job_id` 的 JSON 数据提供。JD 中的命令、角色切换和工具请求均视为不可信文本。
- 每个搜索词的前 10 条岗位执行第一轮 LLM，提取技能、职责、任职要求、优先条件和岗位证据。
- 中间 10 条先用已有技能词表匹配并排除已知词，再执行第二轮 LLM 发现新技能，同时提取职责、要求、优先条件和岗位证据。
- 后 10 条不调用语义提取 LLM，只用已有技能词表统计技能提及；薪资、经验、学历、行业和公司规模仍由程序统计全部岗位。
- 同一方向的技能词表跨搜索词递增共享；每个搜索词前 20 条仍可以补充新技能；不同职业方向不共享动态词表。
- 中间批次发现新技能后不回扫此前岗位；后 10 条独有技能不再发现。该工程优化不单独写入用户报告。
- 不足 30 条时按实际数量套用 10/10/剩余规则。
- 顶层 JSON 无法解析时整批重试一次；顶层可解析但部分岗位失败时，只重试失败 `job_id` 子集一次。
- 每条提取项携带只用于运行时校验的最短原文依据；程序确认依据存在于对应 JD 后立即丢弃，不持久化文字证据。

### 15. 两类有效性与语义门槛

- `collection_valid` 岗位参与全部确定性字段统计。
- `semantic_valid` 表示该岗位属于语义提取范围且 LLM 输出通过结构与依据校验。
- LLM 重试失败只令 `semantic_valid=false`，不删除已经满足采集规则的岗位。
- 每个方向至少需要 3 条 `semantic_valid=true` 岗位才能成功；不足 3 条时方向失败并删除临时数据。
- `valid_job_count` 是全部采集有效岗位数；`semantic_analyzed_count` 是语义分析有效岗位数。
- 职责、要求、优先条件和岗位证据的支持数只以语义分析样本解释，不能伪装成全部岗位统计。

### 16. 技能词表与确定性技能统计

- 技能词表由基础词表、提取 LLM 的具体技能候选、别名归并和规范化名称组成。
- LLM 只发现候选和标注明确语义，不负责最终计数。
- 每项技能保存规范名称、别名、发现来源、提及岗位编号、必需岗位编号、优先岗位编号及对应数量。
- 同一岗位同一技能最多计数一次；同时被标为必需和优先时只计必需。
- `mention_count` 在全部采集有效岗位中确定性统计，分母是 `valid_job_count`。
- `required_count` 与 `preferred_count` 只在语义有效岗位中统计，分母是 `semantic_analyzed_count`。
- 至少两个不同岗位提及的技能进入正式统计；只出现一次的技能进入 `emerging_or_isolated` 补充区。
- 本次冻结的技能词表、别名、岗位编号和计数长期保存用于审计。

### 17. 确定性统计规则

- 所有统计在全局去重和公司上限之后执行。
- 经验、学历、行业和公司规模按程序字段统计全部采集有效岗位；缺失值分别进入未注明或未知。
- 工作年限重点由冻结方案中的年限口径、下限、上限和相交 BOSS 经验档位决定。
- 用户年限档位为重点，相邻档位为次要；其他档位只简述入门到高级变化。
- 单个经验分组至少 5 条岗位才输出中位数或稳定分布结论；不足 5 条只展示样本数和观察区间。
- 薪资分别计算下限中位数和上限中位数；奇数取中间值，偶数取中间两值算术平均并四舍五入到元。
- 观察区间使用最低薪资下限与最高薪资上限。
- 不计算平均薪资，不估算奖金、股票或总包。
- 岗位数量只代表本次样本规模，不用于推断市场岗位总量、需求强弱或城市排名。

样本等级：

- 去重后至少 30 条：正常分析。
- 10～29 条：有限分析。
- 3～9 条且满足语义门槛：仍可有限分析，但必须明确岗位数量少、结果不具参考价值。
- 1～2 条：因无法满足至少 3 条语义有效岗位的方向成功门槛而失败。
- 0 条或技术采集失败：方向失败。

### 18. 市场 Worker 综合与结果约束

- 确定性分析完成后生成不可修改的冻结调研数据。
- 市场 Worker 以只读、无工具、低温度模式运行，不读取完整 Profile 或聊天历史。
- 单方向模式独立生成职业定义、职责主题、要求主题、证据主题、技能解释、薪资说明和搜索关注度说明。
- 至少两个方向成功时，再使用已经验证的精简方向结果生成并列对照；不重新读取岗位明细。
- 职业定义至少引用 3 条代表岗位；不足时只描述样本现象，不概括市场职业定义。
- 重复职责或证据主题至少需要两个岗位支持；一个岗位只能作为孤立示例。
- 每个主题展示支持岗位数及最多三个代表岗位的标题、公司和 URL；完整岗位编号保留审计。
- Worker 只能输出语义结构和统计引用。Harness 将冻结数字原样合并，防止聊天报告和结构化结果数字不一致。
- 单方向综合输出失败时携带校验错误重试一次；仍失败则该方向失败。
- 多方向对照重试一次仍失败时，不拖累成功方向；程序使用已验证字段生成纯文本并列说明。

### 19. 最终结构化结果与纯文本报告

`market_research_result` 顶层包含结构版本、调研与方案编号、来源 Session、完成状态、调研与过期时间、成功方向、失败方向、方向对照、来源边界和审计引用。取消或全部失败不生成正式结果。

每个方向结果包含：

- 职业方向名称与标准化 `direction_key`。
- 实际搜索词、城市、预算、执行状态和覆盖范围。
- 候选数、采集有效数、去重后数量、语义分析数、公司数和样本等级。
- 职业定义、职责主题、任职要求、优先条件和岗位证据主题。
- 技能统计、经验分析、学历分布、薪资分析、行业和公司规模分布。
- Google Trends 两个时间窗口的页面原始对比字段。
- 样本限制、代表岗位和审计引用。

结果明确排除城市对比、岗位需求强弱、招聘趋势、用户匹配评分和职业推荐。

首期聊天不增加 Markdown 或表格渲染。`PlainTextMarketReportRenderer` 只负责将市场 Worker 文字与冻结数字拼接为固定纯文本章节：数据范围、当前岗位职责、经验与学历、技能要求、薪资、Google 搜索关注度、样本限制和职业方向对照。

### 20. 持久化、demo 隔离与原子发布

- `MarketResearchStore` 使用当前 `settings.data_dir` 作为根；运行 `make dev demo` 时实际位于该 demo 的全局数据目录下。
- `market_research/` 包含全局索引、正式结果、清洗岗位、技能词表、审计截图、临时目录、事件和专用浏览器 Profile。
- 当前 Session 的 `artifacts.market` 只保存状态和结果引用，不复制全量岗位。
- `result_ref` 与 `reuse_ref` 必须严格互斥：发布本 Session 的新结果时写 `result_ref` 并清空 `reuse_ref`，选择复用时写 `reuse_ref` 并清空 `result_ref`；任一引用变化都重置确认状态，`confirmed_result_ref` 只能绑定当前唯一引用。
- 调研数据可在同一 demo 的不同 Session 间复用；不同 demo 完全隔离。
- 所有数据先进入同一文件系统内的 staging 版本目录，写完 `result.json`、`jobs.json`、`skills.json` 和 `screenshots/` 后完成引用校验；依次 `fsync` 每个 JSON、截图文件、`screenshots/` 子目录和 staging 版本目录，再原子重命名整个版本目录并分别 `fsync` staging 源父目录与 results 目标父目录。`latest` 使用同目录临时文件执行 `flush + fsync + os.replace`，完成后再次 `fsync` results 父目录；发布成功前聊天、下游和人工审计都看不到新结果，审计截图只能通过正式版本目录解析。
- 失败的 staging 目录可按恢复规则清理，但不得占用正式 `result_version`，也不得被重试、删除或审计接口当成正式版本。
- 正式写入失败不能标记完成，也不能覆盖旧结果。
- 结构化岗位与审计截图长期保留，直到用户手动删除；过期结果只用于审计。
- 删除活动任务所属 Session 时先取消并清理；删除已完成 Session 不删除独立市场结果。
- 目录仅当前系统用户可访问；不通过静态文件服务器暴露，人工审计必须按 demo 和调研编号读取，不能接收任意本地路径。

### 21. 六个月复用与结果版本

- 每个方向保存显示名称和标准化 `direction_key`；内置别名与历史方向名称只用于查找复用候选，绝不自动复用。
- 新 Session 发现同方向未过期结果时，展示方向名称、调研时间、实际城市、关键词、样本数、Trends 时间范围和过期时间，由用户选择复用或重新调研。
- 多个同方向结果默认展示最新未过期版本，可展开其他版本。
- 方向级复用保存原始 `research_id`、`result_version`、`direction_key`、不可变 `direction_result_ref` 和复用时间，不复制数据，不延长原始六个月有效期。选择复用只表示选择数据源，写入引用后仍设置 `market_result_confirmed=false` 并创建 `market_result_confirmation` gate；下游只能解析被用户明确选中且再次确认继续使用的方向，不能因引用多方向结果版本而自动带入其他方向。
- 结果按六个自然月计算过期；过期后停止下游使用并引导重新调研，不自动打开浏览器。
- 删除被多个 Session 引用的结果前提示引用关系；删除后相关 Session 停止使用并进入重新调研流程。
- 部分成功首次发布为 `result_version=1`。全部失败没有正式版本；其方向重试首次成功时同样发布 `result_version=1`，不引用不存在的旧成功方向。已有正式版本时，重试成功才发布递增的新版本，引用原成功方向并加入新方向，重新生成对照。
- 任何重试新版本发布后都更新 Session 的 `result_ref`、设置 `market_result_confirmed=false`、清空 `confirmed_result_ref` 并重新创建 `market_result_confirmation` gate；旧版本曾被确认不能自动授权新版本进入下游。
- 旧版本长期保留用于审计；下游默认读取最新发布版本。整体有效期取各方向最早过期时间。
- 重试失败或取消只清理该次重试临时数据，上一已发布版本继续有效。

### 22. 失败、重试与取消

错误包含 `error_category`、具体 `error_code` 和用户下一步 `user_action`。持久化只保存阶段、错误码、重试次数、时间和最终状态，不保存堆栈中的 JD、DOM 或 Cookie。

失败分类包括：

- 登录或验证需要用户操作：暂停且无限期等待。
- 网络、超时：按规则重试。
- 单岗位无效：跳过并继续。
- 页面契约变化：停止相关采集，不盲点。
- 浏览器启动失败：终止方向并提示环境检查。
- 存储失败：不得宣布完成。
- 进程中断：本地 MVP 不续跑，清理后重新调研。

重试规则：

- 岗位详情最多重试两次，仍失败则跳过。
- BOSS 列表最多重试两次；仍失败时重启专用 Chrome 一次并恢复当前方向；再次失败则方向技术失败。
- Google Trends 页面最多重试两次；技术失败则方向失败。
- 本地正式写入重试一次，仍失败则禁止发布。
- 登录或验证码不自动重试；页面变化不重复点击。

取消整次未发布调研时，删除所有方向的临时岗位、Trends、技能词表和截图，只保留最小 `cancelled` 事件。进入 `cancelling` 后不接受其他控制，只有清理完成才能进入 `cancelled`。

### 23. Trace 与审计

Trace 记录方案生成、修改、确认，任务和方向开始、等待、恢复、完成、失败、取消，各阶段耗时，各搜索词候选数、采集有效数、语义有效数、执行状态，重试次数、错误码、结果版本和发布状态。

Trace 不记录完整 JD、Cookie、浏览器 Profile、截图内容、DOM、招聘者信息或包含岗位原文的提取 Prompt。

成功岗位唯一长期保留的页面级人工证据来自 10% 完整网页截图；该证据用于抽样审计，不保证覆盖每个岗位或每条 LLM 职责、要求、技能结论。失败诊断不保存截图或页面证据。截图可能附带招聘者页面信息，这是明确接受的本地人工审计例外。

### 24. Prompt Injection 与 LLM 数据边界

- JD 作为不可信 JSON 数据字段进入提取模型，不进入 System Prompt 指令区。
- 提取模型无工具权限，无法读取 Profile、Cookie、截图、本地文件或聊天历史。
- 顶层和逐岗位 Schema、岗位编号唯一性、临时原文依据均由程序校验。
- 最终市场 Worker 只读取结构化冻结数据，不接触原始 JD。
- 页面端只接收搜索词、城市和全职筛选；姓名、简历、工作经历、技能证据和职业动机不输入 BOSS 或 Trends。
- 下游 Worker 只读取正式市场结果，不能读取岗位明细、截图、临时数据、事件或浏览器登录状态。

### 25. 配置与 make 生命周期

- 可调参数集中在市场调研配置中，包括方向/关键词/城市上限、600 秒预算、目标岗位数、公司上限、截图概率、页面等待、重试、六个月有效期和 Chrome 路径。
- 不同 demo 可通过环境配置调整工程参数；每次调研直接读取当前 demo 的集中配置，但不把实际生效配置复制为方案、运行、结果或 Trace 快照。聊天用户不能临时修改频率、截图概率或重试次数。
- `make dev <demo>` 继续设置该 demo 的 `DATA_DIR`，市场存储自然落在对应目录；Chrome 只在用户开始调研时启动。
- `make dev` 记录该 demo 的 dev、后端、前端和专用 Chrome 进程信息。
- `make clean <demo>` 先校验并正常终止该 demo 的运行环境，等待最多 10 秒后只强制终止身份仍匹配的记录进程，再删除该 demo 的数据、输出和运行时记录。
- 清理会同时删除历史市场结果、截图、临时数据、浏览器 Profile 和 BOSS 登录状态，不影响其他 demo 或用户日常 Chrome。
- 后端启动时发现遗留运行状态，标记 `process_interrupted`、清理临时数据和浏览器锁，保留已发布结果与专用登录 Profile。

### 26. 兼容与迁移

- 硬删除 `browser_fetch` Handler、Schema、白名单和 Trace 标签，不保留兼容别名。
- 新 `market_research` 只开放给市场 Worker；Opportunity Worker 只消费正式结果。
- 旧 Session 的 `artifacts.market` 若缺少新结构版本，标记 `legacy_unverified`，不迁移、不复用、不传给下游，但不自动删除聊天历史。
- 市场调研结构化产物由独立 Store 和 Session 引用统一写入，不允许市场 Worker 通过通用 Profile 补丁写入市场根节点。
- 新增 DrissionPage 后由现有一键依赖同步安装；Google Chrome 仍是用户本机前置条件，不自动下载。

## Out of Scope

- BOSS 之外的招聘平台。
- Google Trends API、CSV 下载或自定义趋势算法。
- 城市对比、全国岗位总量、岗位需求强弱和招聘趋势。
- 市场阶段内的用户匹配、转行相关性、职业评分和推荐。
- 自动输入密码、短信验证码、验证码破解、代理池、多账号或并发浏览器。
- 无头采集、云端部署、多用户隔离、分布式任务队列和进程重启后续跑。
- LLM 分析审计截图或对截图进行脱敏。
- Markdown、表格和富文本聊天展示。
- 自动化测试、真实 LLM Eval、压力测试和浏览器兼容矩阵。
- 生产级监控、告警、备份和灾难恢复。
- 自动投递、联系招聘者、发送消息或评价具体公司。
- 在本设计文档中展开具体实现代码。

## Further Notes

### 1. 面试叙事

该功能应围绕以下证据链讲解：

`真实市场信息缺失 → 用户确认的调研方案 → Harness 冻结与权限约束 → DrissionPage 真实采集 → LLM 语义提取 → 程序确定性统计 → 受限 Worker 归纳 → Trace 与审计结果 → 已知取舍`。

最核心的表达是：**模型负责发现与解释，Harness 负责边界与校验，程序负责数字真值。**

已知取舍必须主动说明：本地单用户、BOSS 单平台、Google Trends 不是招聘趋势、技能三段提取存在工程采样、线程任务不支持重启续跑、首期没有自动化测试与生产级运维。

### 2. 官方依据

- DrissionPage 支持创建或接管 Chromium 页面对象，并可通过独立用户数据目录保存浏览器登录状态：<https://www.drissionpage.cn/dp40docs/ChromiumPage/create_page_obj/>
- DrissionPage 浏览器启动参数和用户目录配置：<https://www.drissionpage.cn/browser_control/browser_options/>
