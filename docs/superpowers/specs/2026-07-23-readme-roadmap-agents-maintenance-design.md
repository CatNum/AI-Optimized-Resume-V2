## 1. 背景与现场证据

当前根 `README.md` 共 403 行，同时承担以下职责：

- 产品定位；
- 首次安装和启动；
- 运行环境说明；
- 14 张实机演示截图及其说明；
- 市场调研主路径；
- 仓库结构；
- 测试命令和历史测试数量；
- 文档索引；
- 当前状态；
- 长期规划、优化点、Todo、核心思考、产品演进和设计示例。

这些信息本身有保留价值，但当前组织方式存在以下问题：

1. 第一屏使用仓库代号 `AI-Optimized-Resume-V2`，不能准确表达当前 Career OS 的产品范围。
2. 安装命令和文档索引出现过早，技术面试官难以先理解项目价值。
3. 快速启动信息在开头和“快速开始”章节重复。
4. 实机演示、产品主链路、市场调研说明和当前状态混合，产品结果与工程设计的边界不清楚。
5. 仓库结构只展示一级目录，不能说明 `agents`、`harness`、`platform` 等核心边界。
6. README 写有“96 个 pytest”，而 `backend/tests/eval/CASES.md` 仍写“94 个”，测试数字已经不一致。
7. “规划”“优化点”“todo”“核心”“产品演进”“示例”约占 150 行，混合了当前边界、历史基线、已完成事项、未确认想法和长期愿景。
8. README 使用 `v0.1` 表示工程阶段，同时又使用 `V2` 表示产品阶段，版本语义冲突。
9. 仓库根目录没有项目级 `AGENTS.md`，README、roadmap、测试证据和文档同步没有持续维护规则。
10. `docs/` 下没有统一的版本路线目录，已实现、进行中、下一版本和长期候选事项没有稳定归档位置。

本规格基于 2026-07-23 的逐项决策讨论形成。后续实施不得重新解释或绕过已确认的结构、版本和信息保留要求。

## 2. 目标读者与核心定位

README 的第一目标读者是：

- 技术面试官；
- 项目评审者。

开发者和未来维护者是第二目标读者。README 应先帮助第一目标读者判断项目价值，再提供运行、代码导航和延伸材料。

### 2.2 产品主标题

README 主标题改为：

```markdown
# Career OS
```

仓库代号 `AI-Optimized-Resume-V2` 作为项目来源信息保留，但不再承担产品主标题职责。

### 2.3 一句话定位

README 第一屏使用以下定位：

> 可控、可观测、可评测的职业规划 AI Agent。

核心工程判断为：

> 模型负责决策，Harness 负责约束；执行过程可追踪，最终效果可评测。

这里：

- “模型负责决策”表示 Coordinator 和 Worker 负责意图分析、业务推理与内容生成；
- “Harness 负责约束”是工程原则的简称；按当前代码，阶段 Gate、会话并发、Tool 权限、Profile 写入边界、任务状态和用户确认分别由 API、Coordinator 与 Harness 中的确定性代码共同控制，不能把所有约束误画成请求先进入 Harness；
- “可追踪”表示运行过程可通过 Task 状态、Trace 和界面状态检查；
- “可评测”表示确定性测试、轨迹评测和真实 LLM Eval 分层验证，不代表当前已经达到未测量的生产指标。

## 3. 设计原则

1. **结果优先**：先展示项目定位、快速启动和完整实机演示，再解释产品流程与内部架构。
2. **信息不丢失**：当前 README 中每条事实、命令、链接、截图、规划项和设计思考都必须有明确去向。
3. **允许信息优化**：可以重组、合并重复、修正过期数据和改写措辞，不要求逐字保留。
4. **禁止静默删除**：无法验证、已经过期或暂时无文件承接的信息，必须标记原因并迁移到合适位置。
5. **实现与规划分离**：只有代码、测试、Trace、截图或运行结果支持的能力才能写成已实现。
6. **版本承诺与候选想法分离**：未确认版本归属的想法不得自动进入 `v2.2`。
7. **文档面向人，AGENTS.md 面向 Agent**：README 保持人类读者主线；维护细节和强制同步规则写入根 `AGENTS.md`。
8. **架构图以当前实现为准**：现有架构文档只能作为候选来源，不能在未核对代码时直接复制。
9. **测试结果可复现**：测试数量、通过率和失败结论必须绑定日期与命令。
10. **历史语义稳定**：旧设计文档中的 `v0.1` 是历史架构基线，不做全仓机械替换。

### 5.2 快速开始

本章采用“最短启动路径在前，完整运行说明在后”的结构。

最短启动路径必须覆盖：

1. 环境要求；
2. 安装依赖；
3. 创建并配置 `backend/.env`；
4. 使用 `make dev <suffix>` 启动；
5. 访问前端地址。

完整运行说明继续保留：

- `blank`、`test`、`demo` 和自定义后缀的用途；
- `backend/data/{suffix}/` 与 `backend/output/{suffix}/` 的数据位置；
- `profile.json` 空结构和示例文件边界；
- `make clean <suffix>` 的行为；
- 进程身份复核、TERM/KILL 顺序和最长等待时间；
- 清理范围不会影响日常 Chrome 和其他环境；
- 浏览器旧会话处理方式；
- 从项目根目录分别启动后端和前端的方法；命令必须使用独立子 Shell 或明确目录切换，不能在进入 `backend/` 后继续执行错误的 `cd web`；
- 端口冲突覆盖方式；
- 市场调研静态与前端构建检查命令。

重复命令合并为一次权威说明，任何独有参数、路径、清理边界和安全说明不得删除。

### 5.4 多级仓库结构

仓库结构只展示目录，不展示任何文件。

目录树规则：

- 按架构价值选择性展开；
- 最深五级；
- 展示 `backend`、`web`、`.agent`、`config`、`docs` 和 `scripts` 等主要目录；
- 展示 `agents`、`harness`、`platform`、`runtime`、`tests` 等关键职责边界；

- 每个展示目录必须附带简短职责说明。

目录职责说明必须解释“含义 + 作用”。例如：

- `agents`：Agent 模型编排层，负责 Coordinator 和 Worker 的模型运行；

### 5.5 产品主链路

本章使用四阶段表格，不重复实机演示的截图叙述。

| 阶段 | 用户输入 | 系统行为 | 可验证产出 | 关键约束 |
|------|----------|----------|------------|----------|
| 职业初探 | 简历、目标与偏好 | 补全职业上下文 | 结构化职业档案 | 信息不足不得越级 |
| 市场调研 | 方向、城市与筛选条件 | 浏览器采集并分析岗位 | 市场调研结果 | 方案确认后才执行 |

- “用户输入”：阶段开始前需要用户提供或确认的信息；
- “系统行为”：Agent、API、Coordinator、Harness 和 Tool 实际执行的动作；
- “可验证产出”：能从页面、文件、状态或 Trace 检查的结果；

- `waiting_user` 人工验证状态；
- 安全取消；
- 普通 assistant 消息展示报告；
- 正式结果再次确认；
- 同环境其他 Session 的复用候选规则；

README 放置两张精简 Mermaid 图。

#### 系统架构图

必须展示：

- 用户；
- Web 前端；
- FastAPI API；
- ChatOrchestrator；
- Harness；
- Coordinator；
- Workers；
- 平台服务；
- 本地存储；
- LLM；
- Browser。

#### 关键请求时序图

必须展示：

1. 用户从 Web 发送消息；
2. Web 调用 FastAPI；
3. API 建立或续接 Session，并通过 ChatOrchestrator 管理单 Session 并发与上下文提醒；
4. API 直接调用 Coordinator 执行本轮分析；
5. Coordinator 分析意图并形成 Worker 队列；
6. 必要时由 Coordinator 通过 Harness 委托 Worker；
7. Worker 通过 Harness 授权的 Tool 和平台服务读写；
8. Task 和 Trace 记录执行状态；
9. Coordinator 图先形成确定性回复草稿，API 再以 Coordinator 角色调用 LLM 合成最终正文；
10. API 通过 SSE 向前端流式交付 token 和 done 事件。

当前代码不得画成 `FastAPI → Harness → Coordinator`。真实主链是
`FastAPI → Coordinator → Harness → Worker / Tool`；ChatOrchestrator 是 API 侧的会话运行控制与上下文提醒组件，不是进入 Coordinator 的中间层。

现有候选来源：

- `docs/architecture/00-架构总览.md` 的系统上下文图；
- `docs/architecture/00-架构总览.md` 的核心运行时序；
- `docs/architecture/03-系统分层.md` 的分层架构图。

实施前必须对照当前 `api`、`harness`、`agents`、`platform`、`runtime` 和前端 SSE 代码校准。详细分层图继续留在架构文档，不复制进 README。

### 5.7 核心工程设计

本章使用“工程问题 → 设计机制 → 代码或运行证据 → 当前边界”的表格。

| 工程问题 | 设计机制 | 代码或运行证据 | 当前边界 |
|----------|----------|----------------|----------|
| 模型如何做决策 | Coordinator 分析、派工、合成；Worker 执行业务推理 | 调用链、结构化结果、演示流程 | Worker 调用契约仍在升级 |
| 如何防止 Agent 越权 | Gate、Tool 权限、Profile 写入白名单、用户确认 | 越级拦截截图、权限测试 | 全局失败机制尚未落地 |

字段含义：

- “工程问题”：项目需要解决的真实失控或质量问题；
- “设计机制”：代码如何解决该问题；
- “代码或运行证据”：支持该说法的实现、测试、Trace、截图或文档；
- “当前边界”：尚未实现、尚未验证或明确不在当前版本范围内的部分。

技术栈只在机制需要时出现，不单独堆砌 LangGraph、ReAct、RAG、MCP 等名词。

### 5.8 测试与评测

本章使用“测试命令 + 最近验证快照”。

必须分别说明：

- L1 确定性测试；
- LLM Eval；
- 前端构建或其他相关检查；
- API Key 等运行前提。

最近验证快照至少包含：

| 字段 | 含义 | 作用 |
|------|------|------|
| 验证日期 | 实际执行命令的日期 | 判断结果是否可能过期 |
| 执行命令 | 完整可复现命令 | 让读者能够复跑 |
| 通过数 | 成功测试数量 | 描述已验证范围 |
| 失败数 | 失败测试数量 | 防止把局部通过写成全绿 |
| 跳过或未选择数 | 未在本轮执行的测试数量 | 说明验证边界 |
| 备注 | 失败原因、环境限制或 Key 要求 | 解释结果，不粉饰结论 |

实施时必须实际运行相关命令。若测试失败：

- 如实写入失败数量和主要原因；
- 不使用“全部通过”“生产稳定”“准确率提升”等表述；
- 不因 README 优化任务扩大为代码修复任务；
- 保留 Eval 清单链接。

旧“96”测试数不得静默删除；它由新的可复现快照明确取代，并在迁移核对中记录为过期数据。

### 5.10 当前边界与后续演进

本章分三层：

#### v2.1 当前边界

只展示当前实现已经确认的限制，例如：

- 本地优先；
- 不是生产级 SaaS；
- Worker 强类型调用尚未落地；
- 全局失败机制尚未落地；
- `ChatOrchestrator`（聊天运行协调器）当前使用进程内 `_active_runs`（活动会话运行表）阻止同一 Session 并发；`_chat_stream`（单轮聊天流处理函数）只在正常完成路径调用 `end_chat`（清除活动运行标记），尚未使用 `finally` 覆盖 SSE 中断、LLM 异常等退出路径，异常后可能需要重启进程才能解除该 Session 的运行标记；
- 部分评测和前端 E2E 尚未闭环。

具体内容必须在实施时重新核对代码、测试和版本文档。

#### v2.2 已确认方向

主目标固定为：

> 建立强类型 Worker 调用与全局失败机制，使 Agent 执行从“依赖自然语言猜测职责”升级为“调用契约明确、失败行为一致、执行过程可追踪”。

实施依赖顺序：

1. `WorkerInvocation` 与 `ExecutionPlan`；
2. 全局失败机制；
3. 跨模块系统级回归验证。

其中：

- `WorkerInvocation` 表示一次 Worker 的结构化调用契约，明确 Worker、业务动作、输入、权限和成功条件；
- `ExecutionPlan` 表示 Coordinator 生成并由 Harness 约束执行的节点计划；
- “全局失败机制”表示统一的失败分类、传播、重试、降级、Trace 和用户错误呈现。

#### 长期候选方向

未确认版本归属的长期想法只列摘要并链接到 `docs/roadmap/产品规划与技术演进.md`，不在 README 展开完整 Todo。

## 7. Roadmap 文档体系

### 7.1 目录结构

新增：

```text
docs/
└── roadmap/
    ├── README.md
    ├── 产品规划与技术演进.md
    ├── v2.1.md
    └── v2.2.md
```

目录职责：

- `docs/roadmap/README.md`：版本索引、当前版本、版本号规则和维护方式；
- `docs/roadmap/产品规划与技术演进.md`：跨版本愿景、未确认归属的需求和长期设计思考；
- `docs/roadmap/v2.1.md`：当前开发版本的范围、状态、证据和边界；
- `docs/roadmap/v2.2.md`：下一版本已确认目标、验收标准和实施状态。

`docs/roadmap/` 与 `docs/superpowers/plans/` 的边界：

- roadmap 说明“为什么做、哪一版做、完成到什么程度”；
- Superpowers plan 说明“具体改哪些文件、按什么步骤实施和验证”。

### 7.2 版本号规则

- 当前版本：`v2.1`；
- 后续小版本：`v2.2`、`v2.3`、`v2.4`；
- 下一产品代际：从 `v3.1` 开始；
- `v2.x` 表示第二代 Career OS 产品阶段；
- 旧架构、PRD、Spec 和 Plan 中的 `v0.1` 是历史基线，不机械改名；
- 当前没有 `v2.1` 发布标签，本规格不要求创建 Git 标签。

### 7.3 版本状态

允许状态：

| 状态 | 含义 | 使用条件 |
|------|------|----------|
| 规划中 | 已确认目标，但尚未进入完整实施 | 有明确范围，不能写成已交付 |
| 开发中 | 已经有实现或正在实施，尚未完成全部验收 | 必须区分已完成和进行中 |
| 已完成 | 已满足版本验收标准并留下验证证据 | 不等同于生产级发布 |
| 已归档 | 历史版本，不再接受范围变更 | 只允许修正文档错误或补证据 |

`v2.1` 状态固定为“开发中”；`v2.2` 初始状态为“规划中”。

### 7.4 统一版本文档模板

```markdown
# Career OS v2.x

| 属性 | 内容 |
|---|---|
| 状态 | 开发中 / 规划中 / 已完成 / 已归档 |
| 版本目标 | 本版本主要解决的问题 |
| 最后更新 | YYYY-MM-DD |

## 版本范围
## 已完成
## 进行中
## 验收标准
## 验证证据
## 已知边界
## 非目标
## 变更记录
```

模板字段含义：

- “版本范围”：本版本明确承诺交付的内容；
- “已完成”：已经有实现和证据的内容；
- “进行中”：已开始但尚未通过完整验收的内容；
- “验收标准”：版本从当前状态进入“已完成”必须满足的条件；
- “验证证据”：代码、测试、Trace、截图、Spec 或运行结果链接；
- “已知边界”：当前仍不支持或存在风险的部分；
- “非目标”：明确不属于本版本的事项；
- “变更记录”：记录日期、内容和调整原因。

没有证据的能力只能进入“进行中”或“规划中”，不能进入“已完成”。

## 8. 根 AGENTS.md 设计

### 8.1 格式与作用域

根目录新增唯一的项目级 `AGENTS.md`：

```text
AGENTS.md
```

它遵循 [agents.md](https://agents.md/) 的开放格式：

- 使用标准 Markdown；
- 不依赖私有字段或自定义解析器；
- 放在仓库根目录；
- 作为面向编码 Agent 的项目说明书；
- 显式记录 Agent 应执行的命令、约束和同步维护规则。

本规格暂不新增嵌套 `AGENTS.md`。未来只有在子项目出现与根规则不同的明确需求时才新增，并遵循“离目标文件最近的规则优先”。

### 8.2 必需章节

根 `AGENTS.md` 至少包含：

1. 项目概览；
2. 架构与目录边界；
3. 环境安装和启动命令；
4. 后端、前端和 Skill 修改约束；
5. 测试与验证要求；
6. 安全、隐私和本地数据约束；
7. README 维护规则；
8. Roadmap 与版本维护规则；
9. 文档链接和证据规则；
10. Git 提交信息规则。

### 8.3 README 强制维护规则

`AGENTS.md` 必须要求：

- 已交付能力变化时检查 README、当前版本文档和相关架构文档；
- README 保持本规格定义的十章顺序；
- 实机演示顺序不得随意重排；
- 仓库树只展示目录，选择性展开且最深五级；
- 架构图按当前代码校准；
- 测试数字必须重新运行验证并记录日期与命令；
- 信息迁移建立对应关系，禁止静默删除；
- 无证据的计划不得写成当前能力；
- 产品运行截图使用 `docs/assets/screenshots/`。

### 8.4 Roadmap 强制维护规则

`AGENTS.md` 必须要求：

- 当前实现变化时同步检查当前版本文档；
- 下一版本范围变化时同步检查对应版本文档；
- 未确认版本归属的想法进入《产品规划与技术演进》；
- 版本状态变化必须同时更新 roadmap 索引；
- 版本“已完成”必须满足验收标准并有证据；
- 不批量重命名旧文档中的历史版本；
- roadmap 与 Superpowers plan 保持“版本承诺”和“实施步骤”的边界。

### 8.5 Git 提交信息规则

当用户要求创建 Git commit 时：

- 提交信息整体使用中文；
- 主信息使用 Conventional Commit 风格；
- 格式为“主信息 + 两个及以上具体分点”；
- 分点必须描述实际改动或目的；
- 除非用户明确要求，不使用英文提交信息。

示例：

```text
docs(readme): 重构 Career OS 项目说明

- 按结果优先顺序重组 README 内容
- 新增版本路线与 Agent 文档维护规则
```

## 9. 实施边界

- 在仓库根目录创建临时 `README.before-maintenance.md`，保存实施前 README 完整快照；

若测试暴露代码问题，只记录当前结果和边界；代码修复需要独立授权。

`README.before-maintenance.md` 只是迁移验收工件：创建前必须确认同名文件不存在，不得暂存；完成人工逐段对照后删除，不作为最终仓库文件。

## 10. 验证方案

### 10.1 内容完整性

1. 确认根目录不存在 `README.before-maintenance.md`，再复制当前 `README.md` 形成完整快照。
2. 建立本规格第 6 章的迁移映射。
3. 对 `README.before-maintenance.md` 逐段核对目标位置。
4. 搜索所有原截图路径，确认新 README 仍有引用。
5. 搜索原命令、端口、数据目录和清理规则，确认仍有承接。
6. 搜索原规划项，确认进入版本文档或跨版本规划。
7. 人工确认所有独有信息完成迁移后，删除临时快照。

### 10.2 结构验证

- README 一级章节顺序与本规格完全一致；
- “实机演示”内部顺序不变；
- 仓库树不包含文件；
- 仓库树最深不超过五级；
- roadmap 文件结构完整；
- 根目录只有一份项目级 `AGENTS.md`。

### 10.3 链接与 Markdown

- 检查 README 和新增文档中的相对链接是否存在；
- 对强类型 Worker 调用、受控执行生命周期和全局失败机制的六份依赖文档额外检查 Git 跟踪状态；若仍未跟踪，如实记录“目标在当前工作区存在、由用户后续加入版本库”的临时交付边界，不暂存这些文件，也不把它们误报为本次提交已闭合；
- 检查截图路径是否存在；
- 检查 Mermaid 代码块语法和节点标签；
- 在检查新增文档前，先暂存 `AGENTS.md` 和四份 `docs/roadmap/` 新文件；
- 对已暂存的新文件运行 `git diff --cached --check`，对未暂存的 README 运行 `git diff --check`；
- 人工检查 GitHub Markdown 标题、表格、代码块和 `<details>`（如使用）的闭合。

### 10.4 代码事实与目录树

- 使用当前工作区目录生成候选树，再人工按架构价值裁剪；
- 对照当前代码验证 API、Harness、Coordinator、Worker、平台服务、SSE、Store、Trace 和 Browser 的连线；
- 不以旧架构图替代代码核验。

### 10.5 测试快照

至少尝试：

```bash
cd backend
uv run pytest tests/ -m "not llm" -q
uv run pytest tests/eval/ -m llm -v
```

以及项目当前可用的前端构建或市场检查命令。
